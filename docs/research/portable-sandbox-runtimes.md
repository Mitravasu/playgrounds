# Portable Docker sandbox runtime capabilities

Research for [Survey portable Docker sandbox runtime capabilities](https://github.com/Mitravasu/playgrounds/issues/3), 2026-09-22. This records feasibility and open checks; it does not select a runtime or define the isolation contract.

## Current integration surface

[`SandboxRunner`](../../src/playgrounds/sandbox.py) selects the literal runtime name `playgrounds-runsc` for **both** the root staging container and the unprivileged job container. It creates a named input volume, copies an archive into the staging container, changes its permissions with `exec_run`, and removes the staging container. The job uses `network_mode=none` for offline creator and analyzer work, or the Compose-created internal `playgrounds-analyzer-egress` network for public-URL analysis. It uses a read-only root, two `tmpfs` mounts, read-only input volume, dropped capabilities, `no-new-privileges`, CPU/memory/PID limits, repeated `exec_run` calls for status and output collection, and forced container/volume cleanup. The public-URL path adds `playgrounds-egress-proxy` at fixed IP `172.30.0.2` because of the current gVisor DNS behavior. See [`docker-compose.analyzer-egress.yml`](../../docker-compose.analyzer-egress.yml) and [`sandbox/Dockerfile`](../../sandbox/Dockerfile).

These are ordinary Docker create/exec/volume/network operations, but a runtime still has to implement their behavior for this image. Docker documents the create flags for runtime, read-only root, tmpfs, volume, network, resource limits, and security options. [Docker container create reference](https://docs.docker.com/reference/cli/docker/container/create/). The application does not yet preflight the daemon's runtime registry or prove which runtime actually started.

## Host and runtime facts

| Arrangement | Documented support and setup | Constraint for this repository |
| --- | --- | --- |
| Linux Docker Engine + gVisor | gVisor requires Linux 5.6+, supports x86-64 and ARM64, and documents `runsc install`, a daemon reload/restart, and `docker run --runtime=runsc`. The runtime binary and its sidecar directory must be on the **daemon host**, accessible to the daemon. [gVisor installation](https://gvisor.dev/docs/user_guide/install/), [Docker quick start](https://gvisor.dev/docs/user_guide/quick_start/docker/), [Docker alternative runtimes](https://docs.docker.com/engine/daemon/alternative-runtimes/). | `playgrounds-runsc` is a project-specific daemon registration name; the installer defaults to `runsc`, so setup must register the chosen name explicitly or code must use the installed name. |
| macOS + configurable Linux VM + gVisor | macOS Docker binaries do not include a daemon or runtime environment; Docker Engine must run in a Linux VM or remote Linux machine. gVisor itself requires Linux, so install it **inside** that VM. Colima supports Intel and Apple Silicon Macs, provides Docker in a Linux VM, exposes guest provisioning and Docker daemon configuration, and selects a Docker context. [Docker Engine binary install](https://docs.docker.com/engine/install/binaries/), [gVisor FAQ](https://gvisor.dev/docs/user_guide/faq/), [Colima README](https://github.com/abiosoft/colima/blob/main/README.md), [Colima configuration](https://github.com/abiosoft/colima/blob/main/embedded/defaults/colima.yaml), [Colima FAQ](https://github.com/abiosoft/colima/blob/main/docs/FAQ.md). | This is a plausible same-runtime route, not a tested Playgrounds setup. VM provisioning, daemon registration, guest kernel version, Docker SDK socket, and all three job paths require a smoke test. |
| macOS + Docker Desktop + gVisor | Docker Desktop runs the daemon and containers in a managed Linux VM and exposes daemon JSON settings. Docker's alternative-runtime procedure also requires a shim binary on the daemon host's `PATH`. [Docker Desktop Mac permissions](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/), [Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/), [Docker alternative runtimes](https://docs.docker.com/engine/daemon/alternative-runtimes/). | The cited Docker Desktop docs do **not** document a supported way to persistently install `runsc` and its sidecars inside the managed VM. Changing daemon JSON alone is insufficient. Treat this route as unverified, not impossible. Installing `runsc` on macOS would not install it beside the VM's daemon. |
| Linux Engine + Kata Containers | Kata's current installation guide documents Docker 26+ using its containerd shim and QEMU, with AMD64/ARM64 release archives. Kata requires `/dev/kvm` and virtualization extensions; a VM host needs nested virtualization. [Kata installation](https://github.com/kata-containers/kata-containers/blob/main/docs/installation.md). | Strongly different isolation mechanism, but the Mac Linux VM must expose nested virtualization. Its Docker integration is documented only with QEMU; Playgrounds volume, exec, tmpfs, browser, network, and resource-limit behavior still needs testing. |
| Docker Desktop Enhanced Container Isolation | Docker documents ECI as a Business-subscription feature using Sysbox for user containers. It says existing workflows and images are compatible and `--runtime` is ignored when ECI is enabled. [ECI guide](https://docs.docker.com/enterprise/security/hardened-desktop/enhanced-container-isolation), [ECI FAQ](https://docs.docker.com/enterprise/security/hardened-desktop/enhanced-container-isolation/faq/). | It may be an isolation candidate only if the later contract accepts its threat model and the intended Linux deployment can use the same protection. The current `runtime=playgrounds-runsc` request would **not** prove gVisor use under ECI. Subscription and cross-host deployment remain decisions. |

Docker's normal `runc` runtime is the Engine default. Its standard namespaces/cgroups and a Docker Desktop VM boundary are real isolation layers, but no primary source establishes them as equivalent to gVisor's application-kernel boundary for this project's untrusted generated code. This is an isolation-contract decision, not a shortcut implied by macOS Docker support. [Docker alternative runtimes](https://docs.docker.com/engine/daemon/alternative-runtimes/), [gVisor security model](https://gvisor.dev/docs/architecture_guide/security/), [Docker Desktop Mac permissions](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/).

## gVisor details that affect a Linux VM

- gVisor defaults to `systrap`; its documentation says this often performs better than KVM inside a VM. The KVM platform requires `/dev/kvm` and nested virtualization when the host is a VM. `ptrace` is no longer supported. A macOS Linux VM therefore need not expose nested virtualization to run gVisor with `systrap`. [gVisor platforms](https://gvisor.dev/docs/user_guide/platforms/).
- gVisor warns that Docker user-defined bridge service-name lookup can fail because its network stack cannot reach Docker's embedded DNS. Its documented workarounds include using IP addresses; the repository already pins the proxy to `172.30.0.2`. The fixed subnet may conflict with a user's VM/VPN networks and needs a connectivity test, but gVisor does not itself require replacing this proxy arrangement. [gVisor FAQ](https://gvisor.dev/docs/user_guide/faq/), [`docker-compose.analyzer-egress.yml`](../../docker-compose.analyzer-egress.yml).
- gVisor says it implements only a subset of Linux syscall behavior and recommends trying the actual workload. Its filesystem documentation distinguishes shared external mounts from root filesystem caching; the repository's input archive is copied to a volume **before** job-container creation, which avoids the documented `docker cp` rootfs cache issue, but does not prove volume and `exec_run` compatibility. [gVisor compatibility](https://gvisor.dev/docs/user_guide/compatibility/), [gVisor filesystem](https://gvisor.dev/docs/user_guide/filesystem/), [gVisor FAQ](https://gvisor.dev/docs/user_guide/faq/).
- The Docker Engine can register a containerd shim by `runtimeType` or a runtime binary by `path`; the registration lives with the daemon, not the macOS CLI. [Docker alternative runtimes](https://docs.docker.com/engine/daemon/alternative-runtimes/), [gVisor Docker quick start](https://gvisor.dev/docs/user_guide/quick_start/docker/).

## Verification still needed before selecting an arrangement

1. Define the same isolation requirements for both hosts: boundary against untrusted JS/browser code, allowed egress, host/daemon access, filesystem and artifact transfer, resource containment, and whether a managed VM or Sysbox user namespace satisfies them. gVisor, Kata, and ECI protect different boundaries; the sources do not declare them interchangeable. [gVisor security model](https://gvisor.dev/docs/architecture_guide/security/), [Kata overview](https://github.com/kata-containers/kata-containers/blob/main/README.md), [Docker ECI guide](https://docs.docker.com/enterprise/security/hardened-desktop/enhanced-container-isolation).
2. On a running candidate daemon, inspect `docker info` runtime names and architecture; then test the exact selected runtime with a short container, `exec`, named volume handoff, read-only root/tmpfs, limits, `network=none`, and the internal proxy network. Validate that the runner's Docker SDK reaches that daemon, especially if using a non-default Docker context/socket. [Docker SDK connection guidance for Docker Desktop Linux](https://docs.docker.com/desktop/setup/install/linux/), [Docker create reference](https://docs.docker.com/reference/cli/docker/container/create/).
3. Build and run the image natively on each intended architecture. gVisor supports AMD64/ARM64, but that does not establish that the pinned Node and Playwright image digests or browser payload in [`sandbox/Dockerfile`](../../sandbox/Dockerfile) contain compatible variants. Verify the published manifests and run Chromium smoke jobs on each platform. [gVisor installation](https://gvisor.dev/docs/user_guide/install/), [Docker multi-platform images](https://docs.docker.com/build/building/multi-platform/).
4. Run all job paths end to end. Check `exec_run` polling, archive size/manifest validation, staging permissions, cleanup on failures and timeout, Playwright's Chromium launch, and public HTTPS through the proxy. The current daemon was not running during this research, so no runtime behavior has been verified locally.
